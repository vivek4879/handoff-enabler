# ADR-006: Database migration tool

**Status:** Accepted (on merge)
**Date:** 2026-10-02
**Author:** Vivek (drafted with Claude)

## Context
The schema will grow with every sprint (users and sessions in S1, orders and order history in S2, uploads in S3, processed Stripe events). We need a repeatable, reviewable way to change it, applied the same way on a laptop, in CI, and on Railway.

Constraints from the project rules and earlier ADRs:
- The API already uses the `pg` driver with parameterized queries; there is no ORM (CLAUDE.md, ADR-005).
- Money is integer cents, order history is append-only, processed Stripe event ids are deduplicated (CLAUDE.md). These need database-level guarantees: `CHECK` constraints, unique indexes, and something that blocks `UPDATE`/`DELETE` on the history table (for example a trigger). That is hand-written SQL.
- Production changes must be safe without downtime (expand, then contract) and rollback has to be a considered decision, not an afterthought.
- Dependency rule: explain what a library does, how big and maintained it is, and whether we could write it ourselves in under 50 lines.

## Options considered
### Option A — node-pg-migrate with SQL migrations
A small library that runs ordered migration files against Postgres and records what ran in a table. Migrations can be plain SQL files.
- Pros: we write the real SQL (constraints, triggers, indexes) with no translation layer. Small, focused, and Postgres-specific. Works with the existing `pg` driver.
- Cons: no generated TypeScript types, so row types are written by hand or generated by another tool later. A third-party dependency to keep updated.

### Option B — A hand-rolled runner over plain SQL files
A short script (roughly 50 lines): read numbered `.sql` files, take an advisory lock, apply the ones not recorded in a `schema_migrations` table, each inside a transaction.
- Pros: no dependency, and we understand every line. It would teach exactly how migration tools work.
- Cons: we own its edge cases (locking, partial failures, checksums, a CLI), and it is another piece of code to test. Reinventing a solved problem is a poor use of limited time.

### Option C — Prisma Migrate
- Pros: type-safe client, generated migrations from a schema file.
- Cons: it brings an ORM we decided not to use. Our database-level rules (triggers, partial indexes, append-only history) must be written as raw SQL anyway, and fighting the schema DSL for them is awkward. A heavier dependency and a second abstraction to explain.

### Option D — Drizzle Kit
- Pros: TypeScript schema, generated SQL, lighter than Prisma.
- Cons: still pushes us toward the ORM and a schema DSL for the sake of migrations; the same raw-SQL needs apply.

## Decision
Option A: node-pg-migrate, with each migration written as plain SQL, run through a `pnpm` script in `apps/api`.

## Why
- The most important parts of the schema are SQL-level guarantees, so the tool should let us write SQL directly, not hide it.
- It fits what we already have (`pg`, parameterized queries, a repository layer) and does not introduce an ORM.
- It is small and maintained, which is a better trade than owning a runner (Option B) given the time we want to spend on payments and uploads. Option B stays the fallback if the library ever gets in the way.
- Prisma and Drizzle were rejected because they solve a problem we do not have (type-safe query building) at the cost of making the problem we do have (database guarantees) harder.

## Consequences
- What becomes easier:
  - Every schema change is a reviewed file in a pull request, so schema history is in version control.
  - The same command applies migrations locally, in CI, and on deploy.
- What becomes harder / new risks we accept:
  - Types for query results are written by hand, so a column change can silently drift from its TypeScript type. Repository tests are the safety net.
  - Rollback is not free. Down migrations are for development; in production we move forward with a new migration. Destructive changes (drop a column) follow expand-and-contract: add the new thing, deploy code that uses both, backfill, then remove the old one in a later migration.
  - Migrations run on a live database, so each one must be safe for the previous version of the code still serving requests during a deploy.
- What we must build or monitor:
  - The migration directory and a script (`db:migrate`), then fill in the `DB migrate` command in CLAUDE.md (issue #29).
  - A CI step that applies all migrations to a fresh Postgres service container, so a broken migration fails the pull request.
  - A rule for how migrations run on Railway at deploy time (before the new code starts), and who is notified if one fails.
  - Evaluate the package (size, maintenance, open issues) at implementation time, per the dependency rule.
